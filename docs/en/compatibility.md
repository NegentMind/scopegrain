# Compatibility and official sources

> English translation of the canonical Spanish document
> (`../compatibility.md`). The Spanish version prevails.

Scope: entry points, portable catalog, consultative CLI/MCP and
native bridge proposals for five documented hosts plus one
provisional (Hermes). Documented compatibility does not
certify equivalent behavior across products.

## Host matrix

| Host | Entry point | Generated MCP proposal | Status |
| --- | --- | --- | --- |
| Claude Code | `CLAUDE.md` (root) | `integrations/claude-mcp.json` with `mcpServers.scopegrain` (`type: stdio`) | Documentary; requires user approval in the host |
| Codex | `AGENTS.md` (root) | `integrations/codex-mcp.toml` (`[mcp_servers.scopegrain]`) | Documentary; the project requires trust in Codex |

| Devin Local/CLI | `AGENTS.md` (root) | `integrations/devin-mcp.json` (`mcpServers.scopegrain` without `type`) and `.devin/mcp_config.json` generated by `host activate` (v3000.3+) | Certified pilot in a real Local session (2026-11-17); Devin Cloud is not considered equivalent |
| Google Antigravity | Differentiated App/CLI and IDE proposals; `host activate` requires `--surface app-cli|ide` (`selectionRequired` variants) | `integrations/antigravity-mcp.json` (disabled manual-merge proposal) and `.agents/mcp_config.json` with machine-local absolute paths generated by `host activate --surface ... --apply` | App/CLI pilot certified in a real session (2026-11-19); no IDE pilot nor assumed agents there |

## Notes per source

- **Claude Code:** the project memory is `./CLAUDE.md`. AGENTS.md
  support varies by name precedence across products, which is why an
  explicit entrypoint per host is kept. The fragment uses the
  documented `.mcp.json` format (`mcpServers.<name>.type=stdio`,
  `command`, `args`); the first launch requests approval in the host.
- **Codex:** `AGENTS.md` is loaded from the project root. The TOML
  fragment replicates the `[mcp_servers.<name>]` shape with `command`
  and `args`; absolute paths are used because the cwd context is not
  guaranteed.
- **OpenCode:** `AGENTS.md` is the documented entry point. External
  references in plain text are not expanded automatically, which is
  why the entrypoint instructs reading the instructions file. The
  fragment uses the V2 format `mcp.servers.<name>` with
  `type:"local"`, `command:[...]`, `disabled:true`. A V1 proposal is
  no longer generated; existing V1 files are not deleted. Its former
  path is kept reserved to avoid collisions.
- **Devin Local/CLI:** `AGENTS.md` at the root is the official
  recommendation; Local shares the CLI's customizations. Since Devin
  v3000.3 the project MCP lives in the dedicated file
  `.devin/mcp_config.json` (project scope, shared via VCS);
  `host activate --host devin` generates it as a complete create-only
  file (conflict if a divergent one exists; never overwritten). In
  earlier versions the equivalent was the `mcpServers` key inside
  `.devin/config.json` (old entries are migrated automatically to the
  dedicated file): the `.devin/config.json` native proposal and the
  `integrations/devin-mcp.json` fragment are still generated for that
  manual merge and for the user scope. The user scope is
  `~/.config/devin/mcp_config.json` (`%APPDATA%\devin\mcp_config.json`
  on Windows) and the gitignored local override
  `.devin/mcp_config.local.json`. `.devin/mcp_config.json` contains
  machine absolute paths and is not portable across machines:
  regenerate it per machine with `host activate --host devin --apply`
  after moving the project or the installation (regeneration is
  create-only; if the existing file differs, the plan reports a
  conflict and the owner reconciles — typically by deleting the stale
  file and re-applying). Devin does not expand environment variables
  in this file, so there is no templating. No parity with Devin Cloud
  is claimed.
- **Antigravity:** App/CLI and IDE are not equated. The App/CLI
  proposal includes roles; the IDE one only skills. The `.agents/`
  convention shared with other products provides no isolation. See
  [variants, permissions and sources](native-hosts.md).

## What is NOT done

- Native bridges are generated as proposals under the project's own
  space; no hooks are installed and no permissions, subagents or
  profiles are activated.
- Schema differences and permission scope are documented in
  [native integrations](native-hosts.md); equivalence is not assumed.
- Fragments are not mixed with existing host configurations.
- No server or service is registered; the user reviews and applies
  each proposal manually.
- `serverPath` and the project path (`--project`) are absolute and
  machine-local; `--config` goes as a project-contained relative
  POSIX token (that is what `loadConfig` accepts). This applies to
  ALL generated MCP artifacts: the `integrations/<host>-mcp.*`
  fragments (Claude `.mcp.json`, Codex `[mcp_servers]` TOML, OpenCode
  V2, Devin, Antigravity, Hermes) and also the
  `.devin/mcp_config.json` host file that Devin activation writes at
  the root — none of them is portable across machines. Review and
  reconcile the proposals after moving the installation or the
  project; for `.devin/mcp_config.json` per-machine regeneration is
  `host activate --host devin --apply` (create-only: a divergent
  destination is a conflict, never an overwrite). `doctor` reports
  the stale references; it does not silently fix them nor activate
  the new destination.

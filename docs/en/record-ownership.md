# Creation with proven ownership

> English translation of the canonical Spanish document
> (`../record-ownership.md`). The Spanish version prevails.

Shared ownership semantics for immutable records. A record has
ownership when its source document and its ownership companion were
created in **one recoverable journal operation** and the stored proof
still matches the current bytes. The seam is internal and strict:
`applyJournaledRecordCreation` generates the operation identity only
once and requires every proposed source to be new: an existing matching
file is a conflict, never adoption.

The contract admits four source classes, all at `sourceRevision: 0`:
`capture` (typed notes), `spec` (structured V2 specifications),
`design` (bound V2 designs) and `report` (V2 outcome reports).
`outcome` is the name of the DTO/store/CLI, not a fifth `sourceKind`.
Each class keeps its own error codes and domain labels; the shared
machinery lives in two core modules:

- `src/core/record-ownership-data.mjs`: pure validators, closed objects,
  dense UUID area sets, canonical scope and the nine-field sidecar
  `validateRecordOwnership(value, expectedKind, options)`. The class
  must match `expectedKind` exactly: crossed classes, other classes and
  any revision other than 0 are malformed; there are no defaults or
  normalization for stored documents.
- `src/core/record-ownership.mjs`: the read-only proof
  `readOwnedCreation(bound, descriptor, inspectSource)`, in fixed order:
  bounded sidecar read with binding revalidation, expected
  shape/class checks, scope authorization **before** producing
  content, an operation with a valid commit marker and exactly two
  create events, immutable snapshot equality for both files, a typed
  record built from snapshot copies and a revalidated read of the
  current source that must equal the snapshot. No listings, history or
  adoption of plausible files.

## Owned specification store

`createOwnedSpecificationStore(ctx, options)` binds a resolved context
to a workspace enrollment and exposes exactly `prepare`, `create` and
`get`.

- **Options**: closed `{ areaIds }`, a dense array of workspace area
  UUIDs without repeats. Intentionally there is no `origin` option: the
  artifact and sidecar schemas have nowhere to store it.
- **Input**: closed `{ areaIds, specification }`, both required. The
  outer object is validated before any IO and the nested specification
  is cloned to flat JSON before calling `prepareSpecification`, so a
  later caller mutation cannot alter the record. Record areas are
  normalized to sorted unique IDs and authorized all-of against the
  binding's grants.
- **Paths**: source `<paths.plans>/specs/<uuid>.json`, sidecar
  `<paths.state>/record-ownership/spec/<uuid>.json`. Both are
  newline-terminated formatted JSON; `sourceHash` is the SHA-256 of the
  source's exact bytes. Configured `plans`/`state` paths are honored;
  default directories are never created implicitly.
- **`prepare(input)`**: read-only dry-run with the provisional ID/time
  generated by `prepareSpecification`; validates both destinations
  (links and file ancestors fail) and both document sizes. Returns
  `{ mode: 'dry-run', record, sourceRel, ownershipRel,
  reservesIds: false }`.
- **`create(input)`**: runs `prepareSpecification` inside the strict
  seam callback so the artifact ID is generated only once; only the
  local `createdAt` is aligned to the kernel identity before
  serializing the final bytes. Writes exactly two events (`spec`,
  `record-ownership`) and returns `{ mode: 'applied', record,
  sourceRel, ownershipRel, ownershipConfirmed, journal }`. Uncertain
  receipts are preserved: `ownershipConfirmed` is only true when the
  operation ended committed and confirmed.
- **`get(id)`**: canonical lowercase UUID and then the shared proof.
  The proven snapshot bytes are validated via
  `validateArtifactDocument` (never re-reading via `getSpecification`,
  to avoid a read race) and must be a structured V2 artifact whose ID
  and `createdAt` match the sidecar.

Logical scope and path scope are different concepts: grant areas live
in the sidecar and in the journal events, while `spec.data.scope`
declares the artifact's containment paths and never derives grants.

## Owned design and outcome stores

Two separate typed stores reuse the same proof, without introducing a
generic writer:

| Contract | Design | Outcome |
| --- | --- | --- |
| Factory | `createOwnedDesignStore(ctx, { areaIds })` | `createOwnedOutcomeStore(ctx, { areaIds })` |
| Closed input | `{ areaIds, design }` | `{ areaIds, outcome }` |
| Preparer | `prepareDesign` | `prepareOutcomeEvidence` |
| `sourceKind` | `design` | `report` |
| Source | `<paths.plans>/designs/<uuid>.json` | `<paths.reports>/<uuid>.json` |
| Companion | `<paths.state>/record-ownership/design/<uuid>.json` | `<paths.state>/record-ownership/report/<uuid>.json` |

Both require a resolved context and an enrolled workspace. Options are
the closed object `{ areaIds }`, with no `origin`; config and grants
are privately copied. The frozen store exposes exactly `prepare`,
`create` and `get`. The wrapper is validated before IO, the nested DTO
is cloned to flat JSON and areas are validated as a non-empty dense
array of canonical UUIDs without repeats, sorted and authorized
all-of. Caller-supplied record/operation IDs, revision, destinations or
hashes are not accepted. `specId` and `taskId` are permitted domain
references.

- **`design`** is `prepareDesign`'s closed raw input:
  `{ specId, title, body, references? }`. `specId` must resolve a
  structured V2 specification; the core derives `specDigest` and checks
  the hash binding before serializing. The parent **does not need
  ownership**: a structured spec created by the ordinary flow is valid.
  A V1 or missing spec is not accepted.
- **`outcome`** is `prepareOutcomeEvidence`'s closed raw input:
  `{ taskId, title, body, references? }`. It requires a real formal V2
  task in `REVIEW`, a valid verification and healthy spec/design/plan
  bindings. It derives task, spec, design, plan and verification
  revision and digests; it does not accept caller-declared hashes. It
  keeps `body` verbatim and adds the real task/spec references per the
  existing preparer. Preparation does not require an ACCEPT approval;
  that gate remains later.

The methods keep the same result and receipt shapes as the
specification store:

- **`prepare(input)`** is read-only. It runs the domain preparer,
  checks safe destinations and both document limits, and returns
  `{ mode: 'dry-run', record, sourceRel, ownershipRel,
  reservesIds: false }`. ID and time are provisional: each preview may
  generate another identity and does not reserve or reuse the ID on
  apply.
- **`create(input)`** runs the preparer again inside the strict
  callback; it does not apply a saved preview. This derives the
  parent's current binding or the real REVIEW at creation and
  generates the final ID only once. It aligns the local `createdAt`
  with the kernel identity, serializes newline-terminated formatted
  JSON and computes `sourceHash` over the exact bytes. It creates
  exactly two `create` revision0 events, one `design` or `report` and
  one `record-ownership`, with the same scope. It returns
  `{ mode: 'applied', record, sourceRel, ownershipRel,
  ownershipConfirmed, journal }`; it keeps the complete, uncertain
  receipt. `ownershipConfirmed` is only true if `journal.status` is
  `committed` and `journal.journalState` is `confirmed`.

  Source rollback is best-effort and only attempts to remove files
  created by that application. An uncertain result may keep partial
  sources besides the intent and the snapshots; neither presence nor
  absence of sources proves a commit or authorizes automatic adoption
  or retry.
- **`get(id)`** requires a canonical lowercase UUID and applies the
  shared proof with no fallback. It validates the proven byte copies
  via `validateArtifactDocument`; it requires the expected structured
  V2 type and equality of ID and `createdAt` with the sidecar. It
  returns `{ record, ownership, locator: { operationId, eventId },
  isCurrentSource: true, memoryConsulted: false }`.

The design getter additionally checks the spec binding via
`validateArtifactBindings`, on the already-proven design, **without
re-reading the design via `getArtifact`**. If the parent changes
digest, is missing or stops being valid, the read fails with the
existing domain errors; the ownership proof itself does not exempt that
binding. The binding check runs on the snapshot-derived record before
the final byte comparison of the current source: a combined failure
(parent drifting and source changed at once) may surface the parent's
error first; both cases fail closed.

In contrast, the outcome getter proves the report's present bytes and
its provenance: **it does not re-read the task or re-evaluate its
current bindings**. A later task, state or verification change does not
by itself invalidate the report's byte proof or prove its currency.
`isCurrentSource` means current source equal to the snapshot, not
current eligibility for ACCEPT. The methodology gates keep judging that
currency. Neither preparing inside the callback nor reading the proof
adds serializability across all files or an assertion of active truth.

Version errors remain those of the existing domain and differ per
family: a V1 design is impossible, because `validateArtifactShape`
rejects it as `ARTIFACT_MALFORMED` during snapshot validation inside
the ownership proof; in contrast a structurally valid V1 report under a
genuine committed proof fails as `OWNED_OUTCOME_MALFORMED`, because the
store requires the V2 report with typed data.

## CLI

The boolean `--owned` flag, without a value, selects the ownership
stores. On `specification create|show` it keeps its existing opt-in
behavior. On `design create` and `outcome create` it is optional; the
new `design show` and `outcome show` **require** it. Usage help:

```text
specification create --project PATH --input FILE [--owned] [--apply]
specification show --project PATH UUID [--owned]
design create --project PATH --input FILE [--owned] [--apply]
design show --project PATH UUID --owned
outcome create --project PATH --input FILE [--owned] [--apply]
outcome show --project PATH UUID --owned
```

The specification help note is preserved and a separate one is added:

```text
--owned opts specification create/show into journal ownership; legacy behavior stays unchanged without it
--owned opts design/outcome create/show into journal ownership; new show commands require it
```

`--config REL` still selects an explicit configuration in these
commands; the `plans`, `reports` and `state` paths are the configured
ones. Config selection keeps the rules from
[getting started](../../README.md#getting-started): two configs
require explicit selection and an explicit path has no fallback.
`--input FILE` resolves from the current working directory, not from
the project. There is no `--yes`, `--force`, destination override or
extra positionals. The `create` flags are exactly `--project`,
`--config`, `--input`, `--apply`, `--owned`, with no positionals; the
`show` flags are `--project`, `--config`, `--owned`, with one UUID
positional. `show` accepts neither `--apply` nor `--input`. The new
`design show` and `outcome show` without `--owned` fail with
`INVALID_ARGS` before accessing the context or reading inputs. For
structural reading, `artifact show design UUID` and
`artifact show report UUID` remain: they do not verify or imply
ownership. `--owned` is not accepted in other command families.

### Enrollment and areas

The config must exist and the workspace must be explicitly enrolled.
For a configured but not yet enrolled project:

```powershell
node ./bin/scopegrain.mjs workspace init --project "C:\path\my-project"
node ./bin/scopegrain.mjs workspace init --project "C:\path\my-project" --apply
node ./bin/scopegrain.mjs workspace show --project "C:\path\my-project"
```

The first command only shows the proposal; `--apply` confirms
enrollment. If it already exists, query `workspace show` and use its
IDs. Owned operations neither create nor adopt a workspace implicitly;
without enrollment they fail with `WORKSPACE_NOT_FOUND`.

As in `capture`, the local CLI takes grants for **all** enrolled
workspace areas from its metadata. This does not authenticate an actor
or implement OS ACLs or isolation. Each record must request its own
`areaIds` explicitly and satisfy all-of authorization: every requested
area must be granted. Local grants do not widen the record's areas or
infer a scope from `specification.scope`, the design's parent or the
outcome's task.

### Owned input

Each owned command receives its closed wrapper: `{ areaIds,
specification }`, `{ areaIds, design }` or `{ areaIds, outcome }`, with
no auto-detection. `specification` is `prepareSpecification`'s existing
raw structured input, not a stored artifact or its `data` object.
`design` and `outcome` are their preparers' raw inputs described above;
they likewise accept neither a stored artifact nor its `data` object.
`origin`, record/operation IDs, revision, storage destinations and
caller-supplied hashes are not accepted. Requirement and scenario IDs
do belong to the specification contract.

Complete `owned-spec.json` example: the UUID
`11111111-1111-4111-8111-111111111111` is **only an example value**,
syntactically valid. **REPLACE it with a REAL area UUID returned by
`workspace show`** before use; the example does not work literally just
because it has a valid UUID.

```json
{
  "areaIds": ["11111111-1111-4111-8111-111111111111"],
  "specification": {
    "title": "Validar solicitudes",
    "originalRequest": "Rechazar solicitudes sin titulo.",
    "outcome": {
      "statement": "Las solicitudes sin titulo se rechazan.",
      "evidencePlan": "Comprobar casos con titulo presente y ausente."
    },
    "requirements": [
      {
        "id": "REQ-1",
        "statement": "El titulo debe estar presente.",
        "scenarios": [
          {
            "id": "SC-1",
            "given": "Una solicitud sin titulo",
            "when": "Se valida la solicitud",
            "then": "Se rechaza por titulo ausente"
          }
        ]
      }
    ],
    "scope": ["src"],
    "constraints": [],
    "nonGoals": [],
    "openQuestions": [],
    "references": []
  }
}
```

After replacing the area and reviewing the content:

```powershell
node ./bin/scopegrain.mjs specification create --project "C:\path\my-project" --input owned-spec.json --owned
node ./bin/scopegrain.mjs specification create --project "C:\path\my-project" --input owned-spec.json --owned --apply
```

There is no new static JSON Schema for this wrapper. The core
validators define the owned contract;
`schemas/record-ownership.schema.json` keeps its capture-exclusive
scope: it does not validate spec, design or report sidecars.

### Results and compatibility

The CLI returns the core values verbatim: `prepare` without `--apply`,
`create` with `--apply` and `get` in `show`; it adds no wrapper or
ownership assertions of its own. Creation shapes are those described
above for the store.

- The preview does not write or reserve IDs (`reservesIds: false`);
  its identity is provisional and is not reused on apply.
- `--apply` authorizes the typed writes, never executing commands,
  producers or hooks. The result keeps the complete `journal` receipt
  and its uncertainty; `ownershipConfirmed` is only true with a
  committed and confirmed operation. Do not blindly retry an uncertain
  result.
- `show --owned` takes the real `record.id` UUID returned at creation,
  canonical lowercase. It returns `{ record, ownership,
  locator: { operationId, eventId }, isCurrentSource: true,
  memoryConsulted: false }` only after proving commit and current
  bytes. If the proof is missing or there is drift, it fails closed: it
  does not query the legacy getter, history or memory, nor adopt
  plausible files or sidecars.

Without `--owned`, valid legacy creations remain the default even if a
workspace exists; they do not require enrollment. Each `create` takes
the preparer's raw input directly, without the `areaIds`/`specification`,
`areaIds`/`design` or `areaIds`/`outcome` wrapper, and keeps the legacy
bytes, input shape and result (`artifact`, `applied`, `files`), without
creating ownership or journal. The mode is not auto-detected from the
input. `specification show` without `--owned` keeps its structural
read; for design/report the existing generic `artifact show` command
is used. Those reads can read an owned V2, but they neither verify nor
imply its ownership proof. The new `design show` and `outcome show` do
not introduce a second structural getter.

### UTF8 JSON input

The CLI's common JSON reader, not only owned mode, bounds bytes first:
`INPUT_TOO_LARGE` prevails over any encoding error. Within the limit,
invalid UTF8 is rejected with `MALFORMED_JSON` before JSON parsing,
with the same message shape as a syntax error; invalid bytes are not
silently replaced with U+FFFD.

Valid literal U+FFFD, precomposed or combined accents, emojis,
surrogate escapes and CRLF endings remain accepted without normalizing
the text. The BOM is not stripped: it keeps `JSON.parse`'s rejection
with `MALFORMED_JSON`. Existing file-safety checks do not change.

## Errors

- `INVALID_OWNED_SPEC_INPUT`: constructor, outer DTO, areas and UUID.
- `OWNED_SPEC_NOT_FOUND`, `OWNED_SPEC_MALFORMED`,
  `OWNED_SPEC_NOT_COMMITTED`, `OWNED_SPEC_SOURCE_CHANGED`: the proof's
  phases in order: missing or non-regular files, forged or mismatched
  records, operations without commit and altered sources.
- Design keeps its own families `INVALID_OWNED_DESIGN_INPUT`,
  `OWNED_DESIGN_NOT_FOUND`, `OWNED_DESIGN_MALFORMED`,
  `OWNED_DESIGN_NOT_COMMITTED` and `OWNED_DESIGN_SOURCE_CHANGED`.
- Outcome uses `INVALID_OWNED_OUTCOME_INPUT`, `OWNED_OUTCOME_NOT_FOUND`,
  `OWNED_OUTCOME_MALFORMED`, `OWNED_OUTCOME_NOT_COMMITTED` and
  `OWNED_OUTCOME_SOURCE_CHANGED`, even though its `sourceKind` is
  `report`. A V1 report does not satisfy the owned outcome contract.
- Existing domain errors keep their meaning: `SCOPE_DENIED`,
  `WORKSPACE_STALE`, `SYMLINK_REJECTED`, `FILE_ANCESTOR`,
  `DOCUMENT_TOO_LARGE`, `JOURNAL_*`, `ARTIFACT_MALFORMED`,
  `SPEC_STRUCTURED_REQUIRED` and the typed input families. A design
  parent with a different digest produces `ARTIFACT_DRIFT`; if missing,
  `ARTIFACT_NOT_FOUND`; if V1, `SPEC_STRUCTURED_REQUIRED`; if
  malformed, it keeps its existing error. A non-formal/out-of-REVIEW
  task, missing verification or unhealthy bindings fail outcome
  preparation with `OUTCOME_INVALID`; a malformed verification keeps
  `INVALID_EVIDENCE`. Those errors are not translated into a successful
  proof.
- In the CLI, `MALFORMED_JSON` covers invalid syntax and UTF8;
  `INPUT_TOO_LARGE` is checked before decoding. Owned mode requires
  existing enrollment (`WORKSPACE_NOT_FOUND` if missing). Omitting
  `--owned` in the new `design show`/`outcome show` is `INVALID_ARGS`,
  not an automatic mode selection.
- The mutable families use the same per-domain scheme:
  `INVALID_OWNED_<X>_INPUT` plus `OWNED_<X>_NOT_FOUND`,
  `OWNED_<X>_MALFORMED`, `OWNED_<X>_NOT_COMMITTED` and
  `OWNED_<X>_SOURCE_CHANGED`, with the specific exceptions listed in
  [Mutable ownership with journal history](#mutable-ownership-with-journal-history).
- **Unified stale-revision convention**: all five mutable stores use
  `REVISION_MISMATCH` when `expectedRevision` does not equal the proven
  current revision. This is a **public behavior change**: the plan
  store previously emitted `OWNED_PLAN_REVISION_CONFLICT` for this
  case. The convention does not cover byte races (the kernel CAS
  `JOURNAL_SOURCE_CONFLICT`), binding invalidation (`WORKSPACE_STALE`),
  stale approval targets (`APPROVAL_STALE_TARGET`) or domain conflicts
  (`OWNED_PLAN_CONFLICT`), which keep their codes.

## Mutable ownership with journal history

Five opt-in stores extend the same proof to records that change. The
new seam is `applyJournaledRecordUpdate(bound, callback)` in
`src/core/journal.mjs`, the strict twin of
`applyJournaledRecordCreation`: the kernel generates the operation
identity only once, hands a frozen copy to the trusted synchronous
callback and validates the returned value as update changes in closed
form. Each change declares `previousHash` (SHA-256 of the expected
current bytes) and `sourceRevision` (the expected current revision);
the byte CAS is checked before the lock, again under the lock before
reserving sequences and once more after temp staging and before the
renames (two-phase apply: temp fsync next to the destination, CAS
re-check of all targets, rename of all and byte post-verification).
A missing, non-regular or byte-different destination is
`JOURNAL_SOURCE_CONFLICT` before consuming journal state. A change
whose content equals the current bytes is filtered out; if all are,
the result is `unchanged` with no operation. Pre-images are persisted
as additional content-addressed snapshots under the `previousHash`
hash (audit; there is no automatic restore) and uncertain receipts
are preserved as in create. There are no mixed operations: `create`
only accepts new sources and `update` only CAS-existing destinations.

`src/core/record-history.mjs` provides the model's pure validators:
`validateUpdateChange` (closed change shape: mandatory integer
`sourceRevision` and sha256 `previousHash`),
`resultingSourceRevision` (create keeps the declared one; update
produces the expected + 1) and `validateRecordTransition` (an update
event must name the same record, expect the revision produced by the
previous event and chain `previousHash` to its `sourceHash`). The
journal keeps no per-record index: the declared `sourceRevision` is
provenance metadata the kernel does not verify against previous
operations; chain coherence is a read-model check.

Shared invariants of the five stores: closed `{ areaIds }` options,
authentic binding and private config copy, scope authorized before
producing content, domain gates inside the kernel callback (before
reserving journal state), frozen stores, fail-closed `get` that
re-proves the whole committed chain, and never listings, history
fallback as current or adoption of plausible files. Genesis and
mutations are one- or two-event operations per store: two rev0
creates for the source+sidecar pair; two updates when the sidecar is
mutable. Only lazy workspace enrollment uses a single-event create
(the pointer). All keep the complete `journal` receipt, including the
uncertain one.

The proof's mechanical machinery lives exactly once in
`src/core/owned-chain.mjs`: bounded current-file reads under a
revalidated binding, strict UTF-8 serialization/parsing, the
two-event-per-operation pair check, create/update chain coherence via
`validateRecordTransition`, the forward walk over the dense index
(`chain`/`operations`) and the backward walk over `previousOperationId`
links. Domain validators, sidecar shapes and business gates stay local
to each store.

| Store | Factory and API | Sidecar | Operations |
| --- | --- | --- | --- |
| Task | `createOwnedTaskStore(ctx, { areaIds })` (`src/core/transition.mjs`): `prepare`, `create`, `get`, `transition` | `<paths.state>/record-ownership/task/<uuid>.json`, mutable with `chain` | create: 2 rev0 creates (`task` + `record-ownership`); transition: 2 updates |
| Approval | `createOwnedApprovalStore` (`src/core/approvals.mjs`): `prepare`, `create`, `get`, `answer` | `<paths.state>/record-ownership/approval/<sha256>.json`, mutable with `chain` | create: 2 rev0 creates; answer: 2 updates (`approval` + `record-ownership`) |
| Session | `createOwnedSessionStore` (`src/core/sessions.mjs`): `prepare`, `create`, `prepareRecord`, `record`, `get`, `resume` | `<paths.state>/session-ownership/<uuid>.json`, mutable chain head | open: 2 rev0 creates (`session` + `session-ownership`); record: 2 updates |
| Plan | `createOwnedPlanStore` (`src/core/plans.mjs`): `prepare`, `create`, `get`, `update` | `<paths.state>/plan-ownership/<key>.json`, mutable with `operations` | create: 2 rev0 creates (`plan` + `plan-ownership`); update: 2 updates |
| Workspace | `createOwnedWorkspaceStore` (`src/core/workspaces.mjs`): `prepare`, `update`, `get` | `<paths.state>/workspace-ownership.json`, mutable pointer | genesis: 1 pointer create; update: 2 updates (`workspace` + `workspace-ownership`) |

### Owned tasks

The source is the same domain `<paths.tasks>/<uuid>.json`, byte
identical; the sidecar uses the `record-ownership/task/` layout with a
local ten-field validator because `OWNERSHIP_KINDS` stays closed to
the immutable kinds. The sidecar is mutable and carries `chain`: a
dense list of operationIds where `chain[k]` produced revision k,
`chain.at(-1) === operationId` and
`chain.length === sourceRevision + 1` (same convention as approvals,
bounded by `maxSessionEvents`).

- **`create`** emits two rev0 create events (`task` and
  `record-ownership`) in one operation; `prepare` is the usual
  dry-run, reserving no IDs.
- **`transition`** takes `{ areaIds, transition }` with the same input
  as `transitionTask`, requires the areas to be exactly the record's
  proven scope (`SCOPE_DENIED` on any difference) and takes the
  `<id>.json.lock` lock to block cooperative legacy writers for the
  whole window. Under that lock it proves the current ownership and
  runs `evaluateTaskTransition` (revision CAS, workflow edge,
  evidence, ACCEPT and methodology gate) inside the kernel callback;
  it emits a two-update-event operation (`task` and sidecar) chained
  to the proven tip.
- **`get`** walks the sidecar's `chain` forward: each referenced
  operation must be committed with exactly two events and both series
  (source and sidecar) validate with `validateRecordTransition` from
  the create; each revision's sidecar snapshot re-proves the `chain`
  prefix. It does not enumerate `journal/operations`. It also requires
  `record.revision ===` `sourceRevision` and current bytes equal to
  the proven tip.
- Errors: `INVALID_OWNED_TASK_INPUT`, `OWNED_TASK_NOT_FOUND`,
  `OWNED_TASK_MALFORMED`, `OWNED_TASK_NOT_COMMITTED` and
  `OWNED_TASK_SOURCE_CHANGED`; the domain codes (`REVISION_MISMATCH`,
  `INVALID_TRANSITION`, `METHODOLOGY_BLOCKED`, `TASK_LOCKED`, ...)
  keep their meaning.

### Owned approvals

The recordId is the approval's sha256 digest, not a UUID; the source
lives at `<paths.decisions>/approvals/<sha256>.json`. The mutable
ten-field sidecar carries `chain`: an ordered list of operationIds
where `chain[k]` produced revision k, `chain.at(-1) === operationId`
and `chain.length === sourceRevision + 1`.

- **`answer`** requires `{ id, answer, expectedRevision,
  expectedTargetDigest, actor }` (optional `comment`) and resolves
  `expectedRevision` to the `sourceHash` of the event that produced
  that revision inside the proven chain, declared as `previousHash`: a
  double answer from the same revision declares stale bytes and the
  kernel rejects it with `JOURNAL_SOURCE_CONFLICT` before reserving
  state. The source event declares the caller's `expectedRevision`;
  the sidecar's, the proven tip revision. The owned store offers no
  `prepareAnswer`; the legacy `prepareApprovalAnswer` still exists
  outside it.
- **`get`** walks the whole chain: each committed operation with
  exactly two events (`approval` + `record-ownership`), chained by
  `validateRecordTransition` in both streams, and each revision's
  sidecar snapshot re-proves its `chain` prefix. The tip record must
  declare `revision === sourceRevision` of the sidecar and the current
  bytes must equal the tip.
- Errors: `INVALID_OWNED_APPROVAL_INPUT` and the `OWNED_APPROVAL_*`
  family (`NOT_FOUND`, `MALFORMED`, `NOT_COMMITTED`,
  `SOURCE_CHANGED`); the domain codes (`APPROVAL_INVALID`,
  `REVISION_MISMATCH`, ...) keep their meaning.

### Owned sessions

The source is the byte-identical legacy document
`<paths.state>/sessions/<uuid>.json`. The sidecar lives under
`session-ownership/` — not under `record-ownership/`, reserved for
immutable rev0 companions — and is the chain's mutable head with
twelve closed keys, including `previousOperationId` and
`createOperationId`. A rev0 sidecar requires
`operationId === createOperationId`,
`previousOperationId === null` and `createdAt === updatedAt`.

- **`create`** (open) is one operation with two rev0 create events
  (`session` + `session-ownership`).
- **`record`** emits one operation with two update events over both
  files. All domain gates — `expectedRevision` CAS, `checkAction`
  against the live task, `used < limit` budget and full prospective
  shape — run inside the kernel callback, before reserving journal
  state. The recorded scope must equal the enrolled scope exactly
  (`INVALID_OWNED_SESSION_INPUT` if it differs). **`prepareRecord`**
  is the dry-run: it proves only the tip (O(1) writes; reads walk the
  chain, deliberate).
- **`get`** does the full backward walk via `previousOperationId`
  down to the rev0 create operation: each committed operation with
  exactly two events, the sidecar snapshot reproduces the linked
  document and both streams pass `validateRecordTransition`.
  **`resume`** returns the proven record plus the task's live state.
- Errors: `INVALID_OWNED_SESSION_INPUT` and `OWNED_SESSION_*`
  (`NOT_FOUND`, `MALFORMED`, `NOT_COMMITTED`, `SOURCE_CHANGED`).

### Owned plans

The source is `<paths.plans>/<key>.json` and the recordId is the
plan's `key`. The mutable eleven-field sidecar carries `operations`,
the append-only list of operationIds:
`operations.length === sourceRevision + 1` and the last one is
`operationId`.

- **`create`** emits two rev0 create events (`plan` +
  `plan-ownership`). Member task files are created before the journal
  operation by the all-or-nothing legacy writer, so an uncertain
  receipt can leave unreferenced inert tasks (documented window; the
  reverse order would leave a committed plan without its tasks,
  strictly worse). An existing owned destination fails first with
  `OWNED_PLAN_CONFLICT`.
- **`update`** takes `{ key, expectedRevision, plan }` — without
  redeclaring areas: the events use the sidecar's proven scope. The
  revision must equal the proven tip (`REVISION_MISMATCH`, formerly
  `OWNED_PLAN_REVISION_CONFLICT`: public behavior change)
  and the whole document is revalidated: shape and DAG, immutable
  provenance fields (`schemaVersion`, `authorContext`, `inputDigest`,
  `createdAt`, `specId`, `designId`), member ids stable per key, new
  members already existing on disk and, in V2 plans, coherent formal
  refs and full scenario coverage (`PLAN_MEMBERSHIP_INVALID`,
  `INVALID_PLAN`). Identical bytes return `{ mode: 'unchanged' }`
  without consuming journal; if they differ, a two-update-event CAS
  operation.
- **`get`** re-proves the whole chain: each committed operation, two
  chained events and a sidecar snapshot byte-reconstructible by
  prefix. Readiness (`nextPlanTasks`) is a derived read over live
  tasks and is not part of the proof.
- Errors: `INVALID_OWNED_PLAN_INPUT`, `OWNED_PLAN_NOT_FOUND`,
  `OWNED_PLAN_MALFORMED`, `OWNED_PLAN_NOT_COMMITTED`,
  `OWNED_PLAN_SOURCE_CHANGED` and `OWNED_PLAN_CONFLICT`, plus the
  legacy domain codes. A stale expected revision uses the unified
  `REVISION_MISMATCH` code.

### Owned workspace

No `create`: explicit enrollment produces the `workspace.json`
descriptor. The proof anchors on the
`<paths.state>/workspace-ownership.json` pointer, with eight closed keys
in `schemaVersion: 2` (`schemaVersion`, `workspaceId`, `revision`,
`sourceHash`, `operationId`, `previousOperationId`, `createOperationId`,
`updatedAt`): each update links the pointer to the previous operation,
like the session chain head, and genesis self-anchors with
`previousOperationId: null` and `createOperationId === operationId`.

- **Lazy journal enrollment**, not migration: the first `update`
  without a pointer creates the genesis operation — a single create
  event on the pointer whose `sourceRevision` is the descriptor's
  current revision and whose `sourceHash` covers its CAS-verified
  current bytes — and then applies the homogeneous two-event update
  (`workspace` + `workspace-ownership`). A never-journaled descriptor
  is not adopted: `get` fails with `OWNED_WORKSPACE_NOT_FOUND`. An
  uncertain genesis receipt is returned as `{ updateApplied: false,
  updateConfirmed: false }` instead of hitting the pending-operation
  barrier.
- **`update`** takes `{ areaIds, workspace }` with `workspace.areas`
  as a total replacement matched by `key`: an existing key keeps its
  area id, a new one gets a fresh UUID. Removing an area is
  deliberately rejected (`INVALID_OWNED_WORKSPACE_INPUT`): the event
  scopes are authorized against the current grants, and a removed
  area could leave pending or historic operations permanently
  unauthorizable, including its recovery.
- The identity fields (`schemaVersion`, `workspaceId`, `projectId`,
  `repositoryId`, `createdAt`) are frozen by construction; the
  declared `sourceRevision` and `previousHash` are derived from bytes
  the store itself read, never from the caller.
- Each committed update changes the descriptor's canonical digest and
  permanently invalidates all live bindings (latched
  `WORKSPACE_STALE`); the store re-binds per call to survive its own
  updates.
- **`get`** does not enumerate operations: the pointer names the tip
  and the **full backward** `previousOperationId` walk re-proves EVERY
  committed operation down to genesis: strict shape (genesis = exactly
  one create event; update = exactly two coherent update events), each
  hop's pointer snapshot must byte-equal the linked document, both
  event streams chain via `validateRecordTransition` (the first update
  declares the genesis-anchored base as its pre-image) and every
  intermediate descriptor snapshot is revalidated with the identity
  fields frozen. The tip descriptor snapshot must equal the present
  bytes. Because every operation's events are scope-reauthorized, `get`
  requires the binding to cover the union of historical scopes: a
  partial grant that does not span some chain operation fails
  `SCOPE_DENIED` (a public change from the tip-only proof).
- Errors: `INVALID_OWNED_WORKSPACE_INPUT`,
  `OWNED_WORKSPACE_NOT_FOUND`, `OWNED_WORKSPACE_MALFORMED`,
  `OWNED_WORKSPACE_NOT_COMMITTED` and
  `OWNED_WORKSPACE_SOURCE_CHANGED`.

### Mutable ownership limits

- No cross-record transactions: an update operation covers the files
  of a single record (source and, where applicable, sidecar), nothing
  more.
- The CAS is cooperative: writers outside the journal can interleave.
  Legacy writers produce byte-identical formats and can still write;
  an external write does not corrupt the journal but invalidates the
  proof — the next `get` or owned write fails closed with
  `*_SOURCE_CHANGED` or `JOURNAL_SOURCE_CONFLICT`. The proof detects
  the change; it neither prevents nor reverts it.
- The declared `sourceRevision` is provenance: the kernel does not
  verify it against previous operations; chain coherence is checked
  on read.
- The mutable owned stores are opt-in core factories: they are not
  wired to the CLI or to MCP.
- The owned approval answer has no `prepareAnswer`; the legacy
  `prepareApprovalAnswer` preview neither produces nor consumes
  ownership.
- Removing workspace areas is not expressible by design (risk of a
  permanent `SCOPE_DENIED` over pending and historic operations).
- Workspace ownership is lazy: without a journal pointer there is no
  proof.
- `plan` create can leave inert member tasks on an uncertain receipt;
  there is no automatic compensation.
- Update pre-images are audit snapshots; no recovery restores them
  automatically.

## Limits

- The immutable `record-ownership/` companions remain limited to
  `capture`, `spec`, `design` and `report` revision 0. Mutable
  documents use the CAS/history protocol described in
  [Mutable ownership with journal history](#mutable-ownership-with-journal-history),
  not fake creates.
- Ownership proves a kernel scoped creation; not authenticated
  identity, authenticity of the original request, active truth or
  deletion permission.
- There is no listing/scan, latest pointer, spec supersession,
  automatic producer or connected hooks. Native activation and VantaDB
  embeddings remain blocked by `7c2c8be`, independently of this CLI
  surface.
- Files without ownership are never adopted: a plausible artifact with
  a sidecar lacking the committed two-event operation has no ownership,
  and legacy V1 artifacts fail the V2 structural requirement. The
  legacy structural getters (getArtifact/getSpecification) validate
  shape and bindings but do not imply ownership.
